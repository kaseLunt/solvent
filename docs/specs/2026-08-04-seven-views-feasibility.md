# Seven-views feasibility audit (Codex program, spec phase)

## (1) Cumulative debt-at-headroom curve — accounts and Σ debt within 2/5/10/25% headroom

- supported_today: True
- exact fields: GET /v1/positions?engine=&sort=headroom&dir=asc&limit=1000&cursor= → positions[].health_factor.wad, positions[].health_factor.num, positions[].health_factor.den, positions[].health_factor.infinite, positions[].total_debt, positions[].value_decimals, positions[].status, positions[].liquidatable, positions[].refusal.code, total_positions, next_cursor, batch.id, refused, refusal, GET /v1/book → engines[].value_decimals, engines[].total_debt, engines[].positions, engines[].refused
- gaps: None blocking — headroom is EXACTLY derivable per row and the walk machinery already exists (web/app/book/useFullBookWalk.ts, WALK_LIMIT=1000). Headroom is a SORT KEY only: there is no `headroom` scalar on PositionSummary. The client derives it as (num−den)/num in bigint — Aave from health_factor.wad against 1e18, debt_manager from health_factor.num/den which IS maxBorrowLT/borrowings (web/lib/headroom.ts is the ruling implementation, and the 2/5/10/25 asks map exactly onto HEADROOM_BAND_EDGES). Two real gaps, both additive: (a) the whole view costs ceil(book/1000) sequential round trips and dies 'outpaced' against a live indexer — MAX_WALK_RESTARTS=3 — so the smallest additive change that makes it robust is a server-side `headroom_histogram` on /v1/book's engine rows carrying the same seven left-closed bands, Σ debt per band at value_decimals, and the counted asides (no-debt / unknown / refused); (b) PositionsResponse echoes engine/sort/limit but NOT `dir` or `min_value` (required list: served_at, batch, engine, sort, limit, refused, refusal, total_positions, positions, next_cursor, notes), so an exported curve cannot prove from the body which direction and filter produced it — echo both, additively.
- honesty notes: Do NOT use per-row liq_distance as the headroom axis. liq_distance is a PRICE-factor distance along the committed axis (kind/scale_factor_num/scale_factor_den/factor_asset); W-HR-A's own header records that it answered `no price path` over ~81% of the $1k+ book, including accounts at HF 1.02 — every sentence true, the headline wrong. That is the exact defect this view exists to replace. Bands are LEFT-CLOSED (a headroom exactly at 2% belongs to [2,5)), decided by cross-multiplication in bigint, never a float. Breached (<0%) is its own leading cell — if it is folded into 'within 2%', the label must say so. no-debt (health_factor.infinite), unknown (no usable threshold/debt pair) and refused rows are NAMED asides, never members of the tightest band and never zeros; counts must satisfy Σ bands + crit + aside = total. Σ debt is bigint at the engine's value_decimals, per engine, never summed across engines. The curve must disclose walk completeness (walked N of M, batch #id) and must REFUSE to draw on a partial, superseded or outpaced walk — a vector spliced across two materializations is not a book.

## (2) Debt concentration / Pareto — share of book held by largest borrowers, low-headroom whales highlighted

- supported_today: True
- exact fields: GET /v1/positions?engine=&sort=debt&dir=desc&limit=1000&cursor= → positions[].account, positions[].total_debt, positions[].value_decimals, positions[].status, positions[].health_factor.num, positions[].health_factor.den, positions[].health_factor.wad, positions[].health_factor.infinite, positions[].liquidatable, total_positions, next_cursor, batch.id, GET /v1/book → engines[].total_debt, engines[].positions, engines[].refused, engines[].refusal
- gaps: The DENOMINATOR is ambiguous and the two candidates are not the same number. /v1/book engines[].total_debt is riskd's persisted rollup over the whole engine; Σ over the walked rows excludes refused rows (total_debt is null on them), rows with a null total, and — if min_value is set — every row under the floor. The view must pick one and say which. No contract change is needed if it uses its own walk's Σ and counts the excluded rows in a named aside; if you want a server-authored denominator that matches the walk exactly, the smallest additive change is a `total_debt_of_counted_rows` field on PositionsResponse (and the `dir`/`min_value` echo noted in view 1).
- honesty notes: A Pareto share is a ratio INSIDE one engine. There is no 'top 10 borrowers of the book' — Aave is USD-8 base currency, Debt Manager is USD-6, and the two are never summed (the /v1/book notes say so verbatim). Refused rows carry no debt number: they are outside the numerator AND the denominator and must be counted in a named aside, never as $0 borrowers at the tail. Every 'top N holds X%' sentence must state N, the engine, the batch id, and the min_value filter in force. The whale highlight joins debt (total_debt) to headroom derived from health_factor — both from the SAME row of the SAME walk; never join a debt-sorted page to a headroom-sorted page, they are different cursors over the same batch and the rank pairing would be invented. A null total is an unknowable, not a small borrower.

## (3) Incremental stress exposure — consecutive waterfall point differences

- supported_today: True
- exact fields: GET /v1/book → waterfall.points[].index, waterfall.points[].factor, waterfall.grid_scale, waterfall.points[].engines[].engine, waterfall.points[].engines[].usd_decimals, waterfall.points[].engines[].newly_eligible_accounts, waterfall.points[].engines[].cumulative_eligible_accounts, waterfall.points[].engines[].cumulative_debt_eligible_usd, waterfall.points[].engines[].cumulative_collateral_at_risk_usd, waterfall.points[].engines[].insolvent_if_liquidated_accounts, waterfall.points[].engines[].cumulative_bad_debt_usd, waterfall.monotonicity.ok, waterfall.monotonicity.engine, waterfall.monotonicity.index, waterfall.monotonicity.factor, waterfall.monotonicity.detail, waterfall.at_risk_note, waterfall.eligibility_note, waterfall.excluded_engines[], waterfall.held_flat[], waterfall.scenario_id, waterfall.scenario_version
- gaps: The DEBT increment is not a served quantity, and the difference is NOT 'the debt that became eligible at this step'. internal/risk/waterfall.go uses a LATCH (crossed[i]): once an account crosses it is counted at every deeper point, and cumulative_debt_eligible_usd re-measures the WHOLE latched set at each grid point. So Δ = (debt of accounts newly latched at this point) + (re-measurement drift on already-latched accounts under the deeper shock). Only the ACCOUNT increment is served exactly — newly_eligible_accounts is latch-based, so Σ over points equals cumulative_eligible_accounts at the last point and the counts partition exactly. Smallest additive change: add `newly_eligible_debt_usd` to WaterfallEngine (the debt of the accounts that crossed AT this point, measured at this point). Then the bar is a served number and the residual drift becomes a second quantity the view can name instead of a silent contaminant.
- honesty notes: Label the bar 'increase in eligible debt between factor a and factor b', never 'debt that became eligible' — until the additive field lands, those are different claims. The monotonicity invariant covers cumulative_debt_eligible_usd ONLY: differencing cumulative_bad_debt_usd or cumulative_collateral_at_risk_usd legitimately yields NEGATIVE steps, and at_risk_note says outright 'do not render it as a monotone accumulation'. If monotonicity.ok is false, mark the named point and stop the series there rather than drawing past it — the server surfaces the violation and never smooths it, and neither may the chart. The grid is env-configurable (SOLVENT_API_WATERFALL_GRID; default 1.0→0.4 in ten-percent steps, seven points) so step width must be read from points[].factor against grid_scale and labeled, never assumed uniform. A withheld engine contributes no row at any point — its absence is the named refusal in waterfall.excluded_engines, never a zero bar. Per engine only; the two USD scales are never summed. Every reading carries waterfall.scenario_id/version and held_flat, because a shocked number read without its out-of-model is a number read wrong.

## VERIFICATION — cross-scenario tornado (book-wide, one measure across the committed set)

- supported_today: False
- exact fields: GET /v1/scenarios → scenarios[].id, scenarios[].label, scenarios[].engines, scenarios[].shocks, scenarios[].out_of_model, scenario_config_version, then N × POST /v1/scenarios/{id}/run-book → engines[].eligible_debt_delta_usd, engines[].bad_debt_delta_usd, engines[].newly_eligible_accounts, engines[].market_realization.execution_shortfall_usd, engines[].market_realization.hfs_unchanged, engines[].projection, engines[].usd_decimals, batch.id

(2) THAT GUARD WILL FIRE OFTEN: the committed set is 15 definitions (internal/risk/scenarios/*.json; LoadScenarios embeds every .json in the directory), each POST a full-book re-measure. SMALLEST ADDITIVE CHANGE: a new route POST /v1/scenarios/run-book taking a list of committed ids and answering ONE envelope with ONE batch and N per-scenario engine rows — atomic by construction, one book read instead of N, additive (new path, no existing shape touched), and it dissolves (1) and (2). An optional `batch` query parameter on the existing route is cheaper but fixes only (1): the pinned batch may already be unservable by request N. Neither fixes (3) — that is a view law, and each bar must carry its own scenario's axis and refuse the zero it cannot honestly draw.
- honesty notes: Note the asymmetry worth stating in the spec: the PER-ADDRESS tornado is already one request — GET /v1/address/{addr}/stress carries the whole committed set with per-address results under one batch envelope. Only the BOOK-WIDE tornado needs N round trips. Also flag a contract-prose drift found while auditing: the /v1/scenarios/{id}/run-book description says 'the same eleven /v1/address/{addr}/stress serves' while internal/risk/scenarios/ holds 15 committed definitions. The run-book example test law (cmd/api/p5_runbook_example_db_test.go: TestRunBookExampleIsAServedBody) pins BODIES against the server, not description prose, so this count drifted unpinned.
